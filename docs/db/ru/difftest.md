# Дифференциальное тестирование против настоящего SQLite

`tools/db/difftest/` прогоняет один корпус SQL через два движка — этот и
настоящий SQLite — и сравнивает ответы строка за строкой.

Правило, без которого всё это не имеет смысла: **расхождение — это находка, а не
допуск.** Каждый запрос в корпусе либо совпадает с SQLite точно, либо имеет
запись в «Известных отличиях» ниже с причиной. Запрос, который расходится и не
вписан туда, — это баг, по определению.

## Как запускать

```sh
sh tools/db/difftest/run.sh      # 56/56 запросов совпадают с SQLite на 2026-10-19
```

- `setup.sql` — схема и данные, один раз на движок;
- `queries.sql` — по одному выражению в строке, по порядку;
- `runner.nim` — этот движок, печатает `q<индекс>\t<строка>||<строка>`;
- `reference.py` — настоящий SQLite через `sqlite3` из Python, печатает то же;
- `run.sh` — собирает, запускает оба, диффит, показывает первые расхождения.

Обе стороны нормализуют одинаково: `NULL` для null, целые десятичные, вещественные
без хвостовых нулей, текст как есть. Ошибки сравниваются как факт отказа, а не как
текст: SQLite говорит `no such column: name`, этот движок — `NOTFOUND`, и ни одна
из формулировок не является свойством совместимости.

## Что нашлось на первом же прогоне

Три настоящих расхождения, и все невидимые для юнит-тестов — потому что тесты
писал тот же человек, что и движок, и закладывал в них те же допущения.

| Запрос | SQLite | Этот движок (было) | Причина |
|---|---|---|---|
| `7 / 2` | `3` | `3.5` | целочисленное деление сохраняло тип только при точном результате |
| `max(1, 2)` | `2` | `1` | любой `max(...)` уходил в агрегатную ветку |
| `cast('42' AS INTEGER)` | `42` | `0` | приведение использовало `asInt`, а он отвечает «как этим индексировать массив» |

Все три исправлены, корпус теперь совпадает 56 из 56.

Первое исправление стоит перечитать. В коде стояло
`if x mod y == 0: return intValue(x div y)  # SQLite: int/int stays int`.
Комментарий был правдой, код делал другое, и ни один юнит-тест не заметил —
потому что тест на деление утверждал `7 / 2 == 3.5`, то есть то же самое неверное
допущение, записанное второй раз.

## Известные отличия (осознанные, с причиной)

| Отличие | Этот движок | SQLite | Почему остаётся |
|---|---|---|---|
| *текст* ошибок | `NOTFOUND`, `LIMIT`, … | фразы | коды — для программ, фразы — для людей; ни то ни другое не контракт |
| порядок строк без `ORDER BY` | порядок вставки/групп | не определён | в SQL он не определён; корпус всегда сортирует там, где это важно |
| типизация | строгая по умолчанию | мягкая | тихая потеря точности — это баг порчи данных; `strict = false` воспроизводит SQLite |
| `Infinity` / `NaN` в real | отвергаются на границе | хранятся как `Inf` | из SQL-текста недостижимо ни там, ни там; разница только в C-интеропе |

## Решение: совместимости с форматом файла SQLite нет

Движок **не** читает и не пишет формат файла SQLite, и это осознанно:

- хранилище здесь своё — страницы 4 КиБ, кадры WAL с CRC32, B+tree из
  `btree.nim`, шифрование страниц со случайными nonce. Формат SQLite — это
  накопление за двадцать лет: унаследованный freelist, арифметика
  overflow-страниц с другими константами, формат записи под собственный
  varint;
- побитовое совпадение означало бы принять каждое из этих решений, включая те,
  ради отказа от которых проект и существует, и заморозило бы раскладку страницы
  до того, как K9L-83 успел бы положить в неё MAC;
- совместимость, которая действительно нужна пользователям, — это **семантика
  SQL** и форма C API, и обе проверяются: корпус выше и есть эта проверка.

Что изменило бы решение: пользователь, которому нужно открыть существующий файл
`.sqlite`. Путь к этому — импортёр, который читает SQLite и пишет этот формат, а
не второй движок хранения внутри этого.
