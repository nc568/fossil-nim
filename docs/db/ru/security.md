# Модель безопасности Foccil DB

Документ описывает **что именно** гарантируется, **чем** это проверяется и **где**
границы этих гарантий.

## 1. Угрозы, которые мы закрываем

| Класс | Пример | Как закрыт |
|---|---|---|
| SQL-инъекция | `"… WHERE name = '" + input + "'"` | В API нет ни одной функции, склеивающей значение в текст запроса. Данные попадают только через параметры |
| Type confusion | вставка `'abc'` в `INTEGER`, «число» из текста | Строгая типизация по умолчанию: потеря приведения — ошибка |
| Побег в файловую систему | `ATTACH`, `load_extension`, `VACUUM INTO` | Отсутствуют. Отвергаются на этапе разбора |
| Тихая опечатка | `load_extention(...)` → NULL | Неизвестная функция = ошибка подготовки выражения |
| DoS через глубину | `((((((…` | Лимит вложенности 64, отдельная ошибка `LIMIT`, не падение стека |
| DoS через объём | `SELECT * FROM big` на 10⁹ строк | Бюджет строк на запрос, ошибка `LIMIT` |
| Целочисленное переполнение | `a + b` с переполнением → отрицательный rowid | Явные проверки, промоушен в REAL вместо заворачивания |
| Повреждение из-за гонки | два писателя | Единственный писатель, транзакции, откат при закрытии соединения |
| Утечка данных в логах | текст ошибки содержит строку таблицы | Ошибки несут код и имя объекта, но не данные строк |
| Небезопасный код в ядре | `ptr`, `cast`, ручные аллокации | Статический тест по исходникам, падает при появлении |

## 2. Коды ошибок (стабильные, для кода, а не для логов)

```
OK GENERIC NOMEM READONLY INTERRUPT IOERR CORRUPT NOTFOUND FULL BUSY LOCKED
SCHEMA TOOBIG CONSTRAINT MISMATCH MISUSE AUTH RANGE SYNTAX UNSUPPORTED TYPE
LIMIT PARAM INJECTION
```

`INJECTION` зарезервирован: он предназначен для слоя, который отвергает динамический SQL,
собранный клиентским кодом (см. п. 4).

## 3. Возможности (capabilities), а не флаги

`DbOptions` при открытии:

| Поле | Смысл |
|---|---|
| `strictTyping` | потеря приведения — ошибка (по умолчанию `true`) |
| `readOnly` | запрет любых записей |
| `allowDdl` | запрет `CREATE/DROP/ALTER` (типично для сервиса с рантайм-SQL) |
| `maxResultRows` | бюджет строк на запрос (0 = без лимита, по умолчанию 1 000 000) |
| `maxParams` | предел числа параметров (защита от «параметров-бомб») |
| `maxQueryMs` | бюджетирование времени (поле есть, включается в v0.2) |

Правильная настройка для «веб-сервис с пользовательскими запросами»:

```nim
let db = openDb(DbOptions(strictTyping: true, readOnly: true, allowDdl: false,
                          maxResultRows: 10_000, maxParams: 100, maxQueryMs: 2_000))
```

## 4. Правило для встраивающего кода

* Значения — **только** через `toParams([...])`. Никакой конкатенации строк.
* Идентификаторы (имена таблиц/колонок) нельзя параметризовать. Если имя приходит извне —
  это белый список, а не строка:

```nim
const AllowedTables = ["orders", "invoices"]
if table notin AllowedTables: raise newException(ValueError, "bad table")
```

* Динамический SQL, собранный из фрагментов, должен проходить через отдельный
  «строгий» режим (запланирован в v0.3, код ошибки `INJECTION`).

## 5. Чем это проверяется

`tests/t_security.nim` — 18 тестов:

1. 12 классических инъекционных payload'ов сохраняются как **данные** и возвращаются
   байт-в-байт;
2. payload в `LIKE` не расширяет шаблон;
3. кавычки в идентификаторах не превращаются в выражения;
4. `;`-хвост после запроса отвергается, а не игнорируется;
5. `allowDdl=false` → `AUTH`;
6. `readOnly` → `READONLY`;
7. `ATTACH`/`load_extension`/`VACUUM INTO` отсутствуют;
8. вложенность 500 → `LIMIT`, не stack overflow;
9. бюджет строк срабатывает;
10. `LIMIT 2^63-1` не аллоцирует;
11. злоупотребление индексами параметров → `RANGE`/`PARAM`;
12. строгая типизация отвергает потери;
13. `NULL` не равен ничему;
14. `UNIQUE` терпит много NULL, но не дубликаты;
15. сообщения ошибок не содержат данных строк;
16. **фаззинг**: 3000 случайных строк — только `DbError`, ни одного падения;
17. **мутационный фаззинг**: 2000 мутаций валидного запроса — то же;
18. **статическая проверка**: в `src/foccil/db/*.nim` нет `ptr`, `cast[`, `addr(`,
    `unsafeAddr`, `alloc*`, `dealloc`.

## 6. Границы гарантий (честно)

* **Файлы на диске не шифруются** в v0.1 (хранилище ещё в памяти). Шифрование страниц
  запланировано в v0.2 вместе с pager — ключ подаётся снаружи, SQL его не видит.
* **Побочных каналов по времени** мы не устраняем: это база данных, а не криптопримитив.
  Для сравнения секретов используйте `constantTimeCompare` из проекта, а не SQL `=`.
* **`random()` не криптостойкий** и помечен как таковой. Криптослучайность в SQL не
  подаётся принципиально: SQL не должен мочь ослабить ключ.
* **Память не защищена от действий процесса-хоста.** Если хост скомпрометирован,
  база скомпрометирована. Цель — не дать скомпрометировать хост через SQL.
