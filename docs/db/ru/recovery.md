# Восстановление после сбоя: что выживает при отключении питания (v0.2, срез 4)

Статус: **реализовано и отфазжено** (2026-10-19). `src/fossil/db/store.nim` связывает
pager и журнал; `tests/db/t_crash.nim` и `tools/db/crash_fuzz.nim` ломают его намеренно.

## Обещание в одну строку

> Транзакция либо присутствует целиком, либо отсутствует целиком. Никогда наполовину.

Всё, что ниже, существует ради того, чтобы это предложение оставалось правдой,
когда процесс умирает посреди записи.

## Как части сходятся

```
          запись               стейджинг              коммит
SQL/B+tree ──► pager ──► грязная страница ──► кадры WAL ──► маркер + 1 fsync
                  │                             │
                  └── кеш ──────────────────────┘
                        побеждает самый свежий образ
```

Pager не импортирует журнал, журнал не импортирует кеш pager'а: `store.nim`
подключает журнал через три хука (`walRead`, `walStage`, `walCommit`). Pager без
журнала ведёт себя ровно как раньше — поэтому тесты хранилища прошли без единой
правки.

## Индекс — не оптимизация

Когда страница ушла в журнал и была вытеснена из кеша, следующее чтение обязано
прийти из журнала, а не из основного файла: основной файл отстаёт на один коммит.
Без `walIndex` (страница → смещение её самого свежего кадра) читатель получает
вчерашнюю строку **без единой ошибки**. Это худший класс багов: он выглядит как
гонка и месяц числится «нестабильным тестом».

## Порядок чекпойнта

1. застейджить и закоммитить всё грязное;
2. вернуть в кеш как грязные все страницы, которые есть только в журнале;
3. записать основной файл, **sync**;
4. увеличить соль, **sync**.

Шага 2 не было в первой версии, и его нашёл фаззер: страницы, ушедшие в журнал и
вытесненные из кеша, **чистые**, поэтому свёртка их пропускала, а смена соли
уничтожала единственную копию. Основной файл оставался со ссылками на страницы,
которые никогда не были записаны.

Два sync намеренно. Если поменять 3 и 4 местами, будут отставлены кадры, которых
в основном файле ещё нет, — сбой между ними потеряет закоммиченную транзакцию, а
это единственное, чего журнал не имеет права делать.

## Как вводится сбой

`Vfs.crashAt` — счётчик байт. Когда запись пересекает порог, она **рвётся**:
на диск попадает только её начало, а все последующие записи отбрасываются. Чтение
продолжает работать, потому что байты никуда не делись.

Разрыв важен. Хранилище, которое теряет только целые записи, никогда не проверит
контрольные суммы, а суммы — это почти вся история восстановления.

## Что фаззер проверяет на самом деле

После перезапуска из `snapshot()` — байтов, лежащих на диске, а не того, чего
хотела программа:

| Проверка | Смысл |
|---|---|
| открывается без исключения | нет «открылось, но нечитаемо» |
| `btree.verify()` проходит | структура всё ещё B+tree |
| у каждого закоммиченного ключа его значение | ни один коммит не потерян |
| транзакция «в полёте» вся внутри или вся снаружи | нет полуприменённого состояния |

Последняя проверка классифицирует ключи **по значению**, а не по наличию: ключ,
закоммиченный ранее и перезаписанный транзакцией в полёте, присутствует в любом
случае, поэтому вопрос «есть ли ключ» отвечает не на тот вопрос.

паритет бэкендов md5 0376a7c4c0dfd8cf602e8fcff9dddb40 (не изменился)

## Два бага, которые породил этот срез, и что их поймало

1. **Утечка при чекпойнте** (выше). Её видно только при сбое *во время чекпойнта*;
   обычное закрытие её не показывает.
2. **CRC в JavaScript.** `int(uint32)` проверяется на диапазон в JS-бэкенде и не
   проверяется в C, поэтому каждая контрольная сумма с установленным старшим битом
   падала с `RangeDefect` в браузере и работала нативно. До этого среза журнал под
   JS вообще не исполнялся. Исправлено приведением через `int32` на границе; тест
   теперь сравнивает суммы как биты, и оба бэкенда дают одинаковые байты.

Был ещё дубликат `putI32`/`getI32` в `wal.nim`, оставшийся с тех пор, как `bytes.nim`
ещё не существовало. Он держал старое, непроверяемое преобразование и расходился с
общим. Две реализации одного порядка байт — это две возможности ошибиться; дубликат
удалён.

## Осознанный компромисс

Файл БД короче одной страницы считается **новым**, если его открывают через путь с
журналом. Это значит либо «никогда не создавался», либо «уничтожен полностью» —
файл меньше 4 КиБ не может содержать ни одной страницы данных. Альтернатива —
отказаться открывать, и тогда сбой при первом создании даёт базу, которую
пользователь больше никогда не откроет. Сам pager остаётся строгим: снисходительность
принадлежит пути, у которого есть журнал, а не формату.

## Чего здесь ещё нет

- обработки отказа fsync (диск, который врёт про свой кеш);
- рваных записей на реальном железе — in-memory VFS рвёт, реальный по заказу нет;
- группового коммита между параллельными писателями: писатель один по замыслу.

## Запуск

```sh
nim c -r --skipParentCfg:on --path:src tests/db/t_crash.nim
nim c -d:release --skipParentCfg:on --path:src tools/db/crash_fuzz.nim && ./build/db/crash_fuzz 1000
```
