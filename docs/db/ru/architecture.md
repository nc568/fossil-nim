# Архитектура Foccil DB

## 1. Принципы

1. **Один источник — три бэкенда.** C, JS, wasm собираются из одного и того же кода.
   Любое решение, которое нельзя выразить в этих трёх мирах, отклоняется.
2. **Ничего лишнего на горячем пути.** Нет GC, нет виртуальной машины, нет реестра
   плагинов, нет строковой сборки SQL внутри ядра.
3. **Безопасность — это свойство конструкции, а не ревью.** Опасные возможности
   отсутствуют, а не «выключены флагом».
4. **Проваливаться закрыто.** Ошибка лучше, чем молчаливая деградация.

## 2. Конвейер

```
SQL ──tokenizer──▶ токены ──parser──▶ AST ──executor──▶ ResultSet
                                  │
                                  └── schema/catalog (таблицы, индексы, ограничения)
```

### 2.1 Токенайзер (`tokenizer.nim`, 336 строк)

* рукописный конечный автомат, без регэкспов (регэксп — это поверхность DoS и лишние
  килобайты);
* токен хранит **срез** исходной строки (`pos`,`len`), а не копию. Лексинг мегабайтного
  запроса = одна аллокация вместо одной на токен;
* числовые литералы декодируются детерминированно: `0x1F`, `1_000`, экспоненты;
  переполнение `int64` переводит литерал в REAL, как в SQLite;
* lookahead ровно на один токен, и он **не откатывает** позицию — иначе каждый `peek`
  пересканирует токен и лексер становится квадратичным (эта ошибка была найдена тестами).

### 2.2 Парсер (`parser.nim`, 1054 строк)

* рекурсивный спуск + приоритетная лестница для выражений;
* арифметика приоритетов: `OR < AND < NOT < сравнения < битовые < ± < */% < || < COLLATE`;
* лимит вложенности 64 — защита от исчерпания стека на `((((((…`;
* всё, что запрещено, отвергается **на этапе разбора**: `ATTACH`, `load_extension`,
  `VACUUM INTO`, неизвестные функции. Это значит, что до исполнителя неудачный SQL не
  доходит вовсе.

### 2.3 AST (`ast.nim`, 246 строк)

Плоский объект с опциональными полями вместо глубокой иерархии вариантов:

* меньше кода (нет посетителей на каждый узел);
* единый размер узла — размер аллокации не «гуляет» по плану;
* сопоставление — один `case` по `kind`, который V8 превращает в jump-table.

Ключевая деталь: **все конструкторы явно выставляют `aggIdx = -1`**. Nim обнуляет поля
объекта, и забытое поле означало бы «это агрегат номер 0» — каждая скалярная функция
возвращала бы NULL. Это ровно тот класс ошибок, который ловит не типизация, а один общий
конструктор.

### 2.4 Исполнитель (`engine.nim`, 1598 строк)

Модель — **дерево с обходом на месте** (tree-walking) над вектором слотов строки.

Почему не байткод-ВМ, как в SQLite:

* ВМ — это ~2.5 тыс. строк реализации опкодов плюс билдер программ;
* на JS/wasm интерпретатор цикла опкодов — худшая форма для JIT (megamorphic switch,
  косвенная диспетчеризация), тогда как прямая рекурсия по маленькому AST инлайнится;
* меньше поверхности атаки: нет счётчика команд, который можно «сломать», и нет таблицы
  опкодов, которую надо держать в синхронизации с парсером.

Цена (повторная подготовка на каждый запуск) снимается кэшем подготовленных выражений:
AST неизменяем после разбора, поэтому один раз разобрали — много раз исполнили.

#### Скоупы

Каждый `SELECT` создаёт **новую область видимости** (пустую карту колонок). Без этого
подзапрос молча делит карту колонок с внешним запросом — это одновременно ошибка
корректности (неоднозначные имена) и утечка информации наружу. Коррелированные
подзапросы разрешаются по цепочке `outer` с ограничением глубины 32.

#### Планировщик

Сейчас — намеренно маленький и **честный**: выбирается не более одного равенства по
индексу (`col = const`), и только если это строго уменьшает набор кандидатов. Всё
остальное — скан. `EXPLAIN` печатает реально выбранный путь (`SEARCH … USING INDEX …`),
и тест это проверяет.

Замер: до планировщика точечный поиск давал **56 запросов/с**, после — **185 842**
(в 3300 раз). Это лучший аргумент в пользу того, что «оптимизация» должна быть
измеримой, а не декларативной.

#### Транзакции

* DML — журнал отмены (`insert/update/delete` + старая строка), откат = проигрывание
  журнала назад, O(изменений);
* DDL — снимок каталога: удалённую таблицу нельзя «вернуть» построчным журналом, потому
  что исчезла её идентичность. Если в транзакции был DDL, откат восстанавливает снимок
  каталога целиком.

### 2.5 Значения (`values.nim`, 333 строки)

* дискриминированный объект: NULL не тащит за собой буфер blob, текст не тащит int;
* полный порядок сравнения: `NULL < числа < текст < blob`, `BOOL` свёрнут в числа,
  чтобы `true == 1`;
* сравнение int/int точное, int/real — аккуратное (без потери больших целых);
* хеш согласован с `==` (иначе `DISTINCT`/`GROUP BY` врут);
* `formatReal` в профиле `foccilMinimalFloat` не тянет libm и даёт **побитово одинаковый**
  вывод на C и на JS.

## 3. Портируемость

| Бэкенд | Как | Ограничения |
|---|---|---|
| C | `nim c --mm:arc` | нет |
| JS | `nim js` | нет (ARC в JS-бэкенде не нужен) |
| wasm32 | `--os:any --cpu:wasm32 --mm:arc -d:useMalloc` + zig (`wasi-libc`, `wasm-ld`) | нет I/O, часы зафиксированы (`-d:foccilNoClock`) |
| cproc/QBE | профиль `-d:foccilMinimalFloat` | блокируется багами cproc, см. `portability.md` |

Всё, что запрещено в ядре, проверяется **тестом**: `tests/t_security.nim` сканирует
`src/foccil/db/*.nim` на `ptr`, `cast[`, `addr(`, `unsafeAddr`, `alloc*`, `dealloc` и
падает, если что-то появилось.

## 4. Что дальше (кратко)

v0.2 — страничное хранилище: pager 4 КиБ, WAL с контрольными суммами кадров, B+tree,
freelist. Это заменит in-memory `std/tables`-хранилище, не меняя исполнитель (интерфейс
`schema.nim` — это и есть граница подмены).

v0.3 — планировщик по стоимости, составные индексы, покрывающие индексы, `EXPLAIN QUERY
PLAN` с оценками.

v0.4 — FTS5-совместимый полнотекст, JSON-функции, оконные функции, триггеры.
