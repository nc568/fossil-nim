# B+tree: формат хранения (v0.2, срез 3)

Статус: **реализовано и протестировано** (2026-10-19). `src/fossil/db/btree.nim`,
`tests/db/t_btree.nim` (24 теста, 5 из них — проверка на модели).

## Два решения, определившие всё остальное

**Ключи всегда лежат на странице.** Ключ в overflow-странице стоил бы случайного
чтения на каждом уровне спуска — худшее место, где можно платить за I/O. Поэтому
ключ ограничен `MaxKeySize = 512` и отвергается сверх лимита громко, а не
обрезается молча.

**Значения выносятся за 1 КиБ.** Ниже этого порога значение едет вместе со
страницей, которую мы и так обязаны прочитать; выше — платим один лишний переход,
и только для тех строк, которым он действительно нужен.

Вместе это ограничивает ячейку 1 544 байтами, значит **любая страница вмещает
минимум две ячейки**. Это и есть инвариант, который делает любое разбиение
завершаемым: узел не может быть «слишком полным, чтобы разделиться». Проверяется
на этапе компиляции, а не на надежде:

```nim
doAssert 2 * MaxLeafCell + NodeHeader + 4 <= PageSize
```

## Раскладка страницы

```
0    u8   тип             1 = лист, 2 = внутренний
2    u16  число ячеек
4    i32  следующий сосед  (цепочка листьев)
8    i32  предыдущий сосед (цепочка листьев)
12   u16  смещение первой ячейки
16   u16  смещения ячеек[n]
       …    ячейки, упакованные от конца страницы назад
```

Ячейка листа: `[keyLen u16][kind u8][pad][valLen i32][key][значение | i32 страница переполнения]`

Ячейка внутреннего узла: `[child i32][keyLen u16][pad][key]`

## Внутренний узел хранит минимум каждого ребёнка

Каждая ячейка внутреннего узла хранит **минимум поддерева своего ребёнка**.
Первая версия хранила только разделитель между двумя соседями, поэтому минимум
ребёнка 0 не существовал нигде. Вставка ключа, понижавшая минимум листа, оставляла
родителя устаревшим, спуск уходил не в ту ветку, и один и тот же ключ оказывался в
двух листьях. Дерево при этом отвечало на большинство запросов правильно — именно
поэтому поймал его тест на модели, а не тест на счастливый путь.

С минимумом на каждого ребёнка при разбиении нечего «поднимать и выбрасывать»:
родитель просто узнаёт минимум нового узла, который тот и так знает.

## Удаление

Схлопываются только **пустые** узлы. Недозаполненные остаются, ровно как в SQLite:
полупустая страница снова заполнится, а слияние стоит записей на нагрузке, которая
обычно состоит из «удалить и вставить заново». Место всё равно возвращается в
единицах, которые умеет переиспользовать список свободных страниц.

Листья связаны в обе стороны, поэтому удаление листа — O(1): `prev.next = next`.
Поиск предыдущего листа спуском от корня превратил бы удаление страницы в обход
дерева.

## Проверка структуры — полноценная функция

`verify()` обходит всё дерево и бросает исключение при любом нарушении: ячейки не
по порядку, ключи вне диапазона поддерева, листья на разной глубине, цепочка
листьев не двусторонняя, узел переполняет страницу, значение переполнения без
цепочки. Каждый тяжёлый тест заканчивается ею. Тест, который проверяет только «get
вернул то, что положил put», прошёл бы и на одностраничном массиве.

`dump()` печатает дерево — писать дешево, а альтернатива при падении структурного
теста — гадать по номерам страниц.

## Ещё два бага, которые стоит помнить

1. После разбиения листа `rhs.right = n.right` перечитывал указатель, который
   `splitOff` уже обнулил: цепочка листьев рвалась пополам, обход заканчивался
   раньше времени.
2. `n.keys[i] = newMin` обновлял **разобранный** массив, а страница собирается из
   сырых байтов ячеек. Минимум родителя молча не доезжал до диска.

Оба не видны при чтении кода и очевидны тесту, который читает обратно то, что сам
записал.

## Чего здесь ещё нет

- карта свободного места на странице (у SQLite список свободных глобальный и
  фрагментированный);
- префиксное сжатие ключей (очевидный следующий выигрыш по месту);
- массовая загрузка для `CREATE INDEX` — сейчас это N вставок, а не сортированная
  сборка;
- конкурентность: один писатель, как и в WAL.
