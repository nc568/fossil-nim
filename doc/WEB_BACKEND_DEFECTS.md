## Дефекты из отчёта

### D1 — `-d:canvas` + `nim js`: тихая пустая страница — **DONE**

**Симптом.** `nim js -d:canvas examples/todo.nim` собирается без ошибок, но в
браузере — белый экран, в консоли тишина.

**Причина.** FFI-объявления канвас-драйвера были написаны так, что Nim
генерировал обращения к несуществующим JS-сущностям: тип элемента объявлялся
как обычный Nim-объект, а не как импортированный. Исключение возникало до
первой отрисовки, страница оставалась пустой, и пользователь не получал
никакой диагностики.

**Исправление.** `JsElement {.importc.} = ref object` — импортированный
opaque-тип, плюс отдельная процедура `jsRenderCanvasFrame`, которой
принадлежит весь вывод кадра. Порядок прагм в Nim важен: прагма должна стоять
**до** имени типа, иначе `Error: invalid indentation`.

**Проверка.** `nim js --mm:arc -d:canvas examples/todo.nim` → `SuccessX`,
366 КБ; `tests/web_canvas_test.nim` → 25/25.

### D2 — метрики шрифта считались как для моноширинного — **DONE**

**Симптом.** Любой шрифт, кроме моноширинного, давал неверную ширину строки:
текст обрезался или оставлял дыры.

**Причина.** `measureText` считал `ширина = число_символов × charWidth`,
то есть предполагал моноширинную сетку. Для пропорционального шрифта это
неверно в обе стороны: `iii` и `MMM` получали одинаковую ширину.

**Исправление.** Скрытый `<span>`-измеритель + кэш `__uirMeasureCache`
(сброс при превышении 16384 записей). Моноширинные семейства по-прежнему
считаются по сетке — это точнее и дешевле; для них в CSS остаётся коррекция
ячейки `letter-spacing:calc(...)`, а для пропорциональных она убрана
(`letter-spacing:normal`): коррекция 1ch имеет смысл только для сетки.

**Проверка.** `tests/web_backend_regression_test.nim` (9 проверок D2,
`-d:html` и `-d:canvas`), `tests/web_html_test.nim` → 57/57.

### D3 — полная перезапись `innerHTML` на каждом кадре — **DONE**

**Симптом.** При каждом кадре DOM уничтожался и создавался заново: мигание,
потеря фокуса и карё, потеря выделения, «съеденные» события ввода. Один
движущийся пиксель перерисовывал тысячи узлов.

**Причина.** Кадр собирался в одну строку `htmlFrameBuffer` и отдавался целиком
через `viewport.innerHTML = frame`. Строка не знает, что из неё уже нарисовано
в DOM, поэтому сравнивать было не с чем.

**Исправлено.** Кадр — это список примитивов, а не строка:

```nim
type
  HtmlPrimKind* = enum
    hpRect, hpPoint, hpLineH, hpLineV, hpSvgLine, hpText, hpImg, hpBlit,
    hpClipOpen, hpClipClose
  HtmlPrim* = object
    kind*: HtmlPrimKind
    style*: string   # атрибут style
    text*: string    # textContent, либо внутренняя разметка svg/img
    extra*: string   # единственный атрибут не-style: viewBox / data-clip
```

Все relay-проки рисования (`htmlFillRect`, `htmlDrawText`, `htmlDrawLine`, …)
складывают примитивы в `htmlPrims`. Дальше пути расходятся:

* **JS** — `jsReconcile(vp, htmlPrims, htmlPrevPrims)` идёт по кадру и живому
  DOM параллельно. Позиция `i` в кадре всегда означает ребёнка `i` текущего
  контейнера, поэтому примитив, равный прошлому на той же позиции, не стоит
  **ни одной** записи в DOM. Стек контейнеров обрабатывает вложенные
  `.uir-clip`. Хвосты, оставшиеся от прошлого кадра, удаляются на каждом
  уровне. `innerHTML` больше не присваивается вообще.
* **Нативный сервер** — `renderPrimsToHtml(prims)` сериализует кадр обратно в
  разметку для SSE-пейлоада, байт в байт как раньше.

Хеш кадра теперь считается прямо по примитивам (`fnv1a64Step` в
`web_common.nim`), поэтому JS-путь промежуточную строку не строит вовсе.
Оба буфера меняются местами через `swap`, так что установившийся кадр не
аллоцирует ничего.

Три тонкости, которые пришлось учесть:

* `<svg>` обязан создаваться через `createElementNS(SVG_NS, "svg")` —
  `createElement("svg")` возвращает `HTMLUnknownElement`, который молча не
  рисует свой `<line>`.
* `className` у SVG-элемента — только для чтения (`SVGAnimatedString`),
  поэтому класс ставится через `setAttribute("class", …)` для всех узлов.
* Переиспользуемый узел нужно **очищать**: элемент, бывший в прошлом кадре
  контейнером `.uir-clip`, а в этом ставший `.uir-rect`, иначе протаскивает
  своих детей дальше (см. N6).

**Результат** (9 приложений × 120 шагов обезьяны, jsdom):

| метрика | значение |
|---|---|
| присваиваний `innerHTML` в viewport | **0** |
| неизменных кадров, где узлы остались теми же объектами | 755–813 |
| кадров, где идентичность узлов нарушилась | **0** |
| расхождений «объявлено узлов / реально в DOM» | **0** из 770 замеров |
| структурная работа относительно полной перезаписи | 0.41–0.57 |

Для сравнения: та же нагрузка с `innerHTML` даёт 0.81 и 19 полных перезаписей
на одном только `calculator` — это измерено мутационным тестом (см. ниже).

**Коалесцирование ввода** осталось с прошлой итерации: последовательные
`MouseMove` схлопываются в одно, `mouseup` доставляется всегда.

### D4 — макрос `{.uirApp.}` выбирал первый попавшийся `while` — **DONE**

**Симптом.** Если в `proc main()` был цикл инициализации перед главным
циклом, макрос превращал в кадровый цикл именно его: приложение молча
выполняло инициализацию и завершалось.

**Причина.** Выбор по первому `nnkWhileStmt` в обходе тела.

**Исправление.** Цикл считается главным, только если он **прямой оператор**
тела `{.uirApp.}` и вызывает `refresh` / `pollEvent` / `waitEvent` / `sleep`.
Если таких циклов несколько, побеждает **последний**. Если нет ни одного —
ошибка компиляции, а не тихое поведение.

**Проверка.** `tests/web_backend_regression_test.nim` компилирует два
контрольных примера: корректный (компилируется) и без цикла (ожидаемая
ошибка компиляции с упоминанием `uirApp`).

### D7 / D8 / D9 — окно диктовало раскладку — **DONE**

- **D7.** Минимальный размер окна задавался константами. Теперь мост читает
  `__uirMinViewport` (пол, по умолчанию 320×240) и клампит оба измерения.
- **D8.** Магические идентификаторы и жёстко прошитый отступ. Теперь
  `__uirViewportInset` — опция, по умолчанию `{x:0, y:0}`.
- **D9.** `devicePixelRatio` применялся к логическому размеру. Теперь он
  влияет только на backing store канваса (`__uirDpr`), логический размер
  остаётся в CSS-пикселях.

**Проверка.** jsdom-обезьяна проверяет контракт моста на каждом приложении,
после шторма ресайзов и после «шторма пола» (запрошен пол 500×400, сцена
сжимается до 1×1 — окно не должно сообщить размер меньше пола).

### D10 — непрозрачная заливка на весь экран стирала кадр — **DONE**

**Симптом.** `fillRect(0, 0, width, height)` непрозрачным цветом в середине
кадра удалял всё, что было нарисовано раньше, — хотя вызывающий код просил
просто прямоугольник на весь экран.

**Причина.** Оптимизация «первая заливка на весь экран = фон, можно начать
кадр заново» применялась по признаку «буфер пуст», но проверялась в момент,
когда буфер уже был очищен этой же заливкой.

**Исправление.** Проверка `htmlFrameBuffer.len == 0` выполняется **до**
добавления примитива.

**Проверка.** Две проверки в `tests/web_backend_regression_test.nim`:
наложение поверх нарисованного сохраняет оба прямоугольника; фоновая заливка
первым примитивом работает как раньше.

### D11 — README про BigInt / `--jsbigint64:off` — **DONE**

В README добавлен раздел «JavaScript target notes». Ключевой факт, который
был не документирован: `--jsbigint64:off` **не работает сам по себе**, он
требует `-d:nimStringHash2`, иначе сборка падает внутри `std/hashes`:

```
Error: Must use `-d:nimStringHash2` when using `--jsbigint64:off`
```

Оба варианта рабочие; смешивать их в одном бандле нельзя.

### D12 — тесты невоспроизводимы на чистом клоне — **DONE**

**Симптом.** Тесты ссылались на `/home/user/...`, `/tmp/...` и `chromium`,
поэтому на чистом клоне падали или пропускались молча.

**Исправление.**
- `tools/export_interactive_html.nim` ищет корень репозитория сам
  (переопределение — `UIRELAYS_ROOT`) и проверяет «zero canvas» политику по
  API-вызовам, а не по словам `<canvas>` / `WebAssembly` (Focim встраивает
  README, где оба слова встречаются в тексте — проверка по словам давала
  ложное срабатывание).
- `tests/monkey_browser_test.nim` и `tests/standalone_html_monkey_test.nim`
  ищут браузер через `UIRELAYS_BROWSER` или `PATH` и, не найдя его, явно
  сообщают **SKIPPED** с указанием, чем заменить.
- Добавлены два браузеронезависимых набора: `tests/server_monkey_test.nim`
  (живой нативный сервер, чистые сокеты) и `tests/jsdom_monkey_test.nim`
  (`node` + `jsdom`). Оба считают пропуски отдельным счётчиком.
- `tools/bootstrap_nim.sh` собирает Nim 2.2.4 из исходников, если на чистом
  клоне его нет (см. N8 — первая версия скрипта не работала).
- Всё это прогоняется на каждом пуше в GitHub Actions (`.github/workflows/ci.yml`),
  так что «воспроизводимо на чистом клоне» — не утверждение, а проверяемый факт.

## Новые дефекты, найденные в процессе

### N1 — сервер терял данные HTTP-запроса

**Симптом.** `POST /input` с 6000 событиями возвращал `ok=false, status=0`,
а `/health` показывал `totalEventsProcessed: 1668` вместо 7200. Всё, что не
влезло в первое чтение, терялось **молча**.

**Причина.** Запрос читался одним вызовом чтения фиксированного размера.

**Исправление.** Чтение до полного заголовка и тела с ограничением на размер;
неполный запрос — `400` или `413`, а не молчаливое усечение.

**Проверка.** Флуд возвращает `200` с `"queued":4096`, растёт
`droppedEvents`; `tests/server_monkey_test.nim` → 56/56.

### N2 — переполнение очереди событий роняло `mouseup`

**Симптом.** При переполненной очереди вновь пришедшее событие отбрасывалось.
Отпускание кнопки мыши терялось, и приложение «залипало» в состоянии нажатия.

**Исправление.** Очередь вытесняет **самый старый `MouseMove`**; пришедшее
событие доставляется всегда. Счётчик `droppedEvents` растёт, чтобы политика
была видна в `/health`.

**Проверка.** Три проверки в `tests/web_backend_regression_test.nim`, включая
случай «очередь забита перемещениями, приходит `mouseup`».

### N3 — битый JSON не учитывался

Малformed тело `/input` парсилось «как получится». Теперь возвращается
`200 {"added":0}` и растёт `inputParseErrors`.

### N4 — утечка файловых дескрипторов на SSE

Отключившиеся SSE-клиенты не убирались. Добавлен `reapSseClients()`; в
`/health` появились `sseClients` и `droppedEvents`. Проверяется сценарием
«24 клиента подключились, затем все собраны» (56/56).

### N5 — HTML-сборка требовала `<canvas>` в оболочке

Отчёт о контракте оболочки включал `#uir-canvas` в обязательные идентификаторы
для **обоих** бекендов. HTML-страница, которой запрещено использовать канвас,
получала предупреждение о его отсутствии и подталкивала встраивающего
добавить элемент, который драйвер использовать не будет.

**Исправление.** Список идентификаторов свой для каждого бекенда
(`__uirShellViewportId`), а обязательные элементы отделены от опциональных:
`__uirMissingElements` — только то, без чего функция мертва (viewport,
`#uir-stage`, `#uir-clipboard-input`); `__uirMissingOptional` — кнопки
тулбара, которых у минимального встраивания может не быть вовсе.

### N6 — reconcile протаскивал детей переиспользованного узла

Найден при проверке D3 собственным тестом, до всякого браузера.

**Симптом.** После сжатия окна в DOM оставались элементы из прошлой, более
широкой раскладки. В `twenty48` кнопка «▲ Slide Up» стояла на `x=1124` и при
холсте 480 px, и при холсте 1020 px — одинаково, то есть её никто не
перерисовывал: узел просто выжил.

**Причина.** Reconcile переиспользует узел, если тег совпадает, а `<div>` —
тег и у `.uir-clip`, и у `.uir-rect`. Когда контейнер в прошлом кадре на этой
позиции становился листовым элементом в этом, ему ставились класс и стиль, но
дети оставались на месте. Зеркальный случай — лист, становящийся контейнером.

**Исправление.** `jsApplyPrim` очищает узел при смене роли:
`textContent = ""` для листовых примитивов и для `hpClipOpen`. Это снимает и
элементы, и текстовые узлы одним присваиванием.

**Как ловится.** Драйвер публикует `window.__uirDomNodeCount` — сколько
элементов кадр должен был положить в viewport. Обезьяний тест сверяет это
число с `viewport.querySelectorAll("*").length` на каждом замере (с поправкой
на `<line>` внутри `<svg>` и `<img>` внутри `.uir-img-crop`: у HTML-элемента
`tagName` в верхнем регистре, у SVG — в нижнем). Утечка даёт расхождение
немедленно.

Мутационный тест: с удалённой очисткой — **85 расхождений из 375**, с ней —
**0 из 770**.

### N7 — приложение не могло объявить свой минимальный размер

**Симптом.** Все восемь примеров запрашивали окно своего проектного размера
(`createWindow(960, 640)`, `createWindow(680, 520)`, …), а в обработчике
ресайза клампились куда ниже — до `max(420, ev.x)`, `max(320, e.x)`.
Содержимое при этом не перестраивалось: у `paint` кнопка «Clear» стояла на
жёстко зашитом `x=474`, у `layout_demo` «[- Remove Pane]» на `x=470`, у
`web_showcase` вторая колонка вкладки графики начиналась с `+200` и
заканчивалась на `+344`. В узком окне всё это уезжало за правый край.

**Почему это дефект бекенда, а не только примеров.** `overflow:hidden` не
делает обрезанное доступным — оно просто невидимо и недостижимо для клика.
При этом пол у viewport уже был (`__uirMinViewport`, по умолчанию 320×240), но
задавать его мог только **встраивающий**. Само приложение сказать «мне нужно
680×520» не могло никак: оставалось клампить собственную переменную `width`,
отчего холст расходился с viewport'ом.

**Исправление.** Новый необязательный relay и публичная прока:

```nim
setMinViewport*(w, h: int)   # src/uirelays/screen.nim
```

* `webSetMinViewport` пишет `window.__uirAppMinViewport` и сразу пересчитывает
  размер, поэтому уже первый кадр рисуется в размере, который приложение
  способно разложить.
* `viewportMin()` в мосту берёт **покомпонентный максимум** двух полов:
  встраивающий может дать приложению больше места, но не может отнять то, без
  чего приложение не рисуется.
* `webInjectResize` поднимает встроенный пол 120 px до заявленного, максимум
  4096 при этом не сдвигается.
* Все восемь примеров теперь вызывают `setMinViewport` со своим проектным
  размером, и их клампы совпадают с ним.

Побочно: `web_showcase` получил адаптивную раскладку (счётчик выравнивается по
правому краю своей панели, а не стоит на `+335`), `paint` — тулбар,
выравниваемый по правому краю и сжимаемый, с обрезкой подписи по месту,
`layout_demo` — кнопки тулбара, раскладываемые от ширины самой панели.

**Эффект.** `maxTextOverflowPx` в jsdom-отчёте упал с **1228 px** до
**68–544 px** в зависимости от seed'а — то есть остаток, который раньше
списывали на артефакт jsdom, почти целиком состоял из настоящих багов
раскладки.

### N8 — `tools/bootstrap_nim.sh` не собирал Nim на чистом клоне

**Симптом.** Скрипт, добавленный как вторая половина D12 («нет Nim — собери
его сам»), в реальности не собирал ничего: на машине без Nim он доходил до
`koch boot` и падал с `./koch: not found`.

**Причины — три, все в одном файле.**

1. В Nim 2.2.x **нет** shell-обёртки `koch`: есть `koch.nim`, который надо
   сначала скомпилировать, а `csources_v2/build.sh` собирает только `bin/nim`.
   Каноническая последовательность — в Nim'овском `build_all.sh`:
   `bin/nim c --noNimblePath --skipUserCfg --skipParentCfg --hints:off koch`,
   и лишь затем `./koch boot -d:release`.
2. `have_nim()` печатала `"ok"` в **stdout**. Контракт скрипта — «stdout это
   ровно путь к годному nim», поэтому `$(sh tools/bootstrap_nim.sh)` возвращал
   *две* строки, и `dirname "$(...)"` в вызывающей обёртке превращался в мусор.
3. `cp -a` копировал всё дерево исходников вместе с `csources_v2` — **2.0 ГБ**,
   из которых 1.8 ГБ сгенерированного C, нужного исключительно чтобы собрать
   bootstrap-компилятор. Кешировать такой каталог бессмысленно.

**Исправление.** `koch.nim` компилируется перед `koch boot`; клон `csources_v2`
и его сборка выполняются только если `bin/nim` ещё нет (иначе повторный запуск
после обрезки заново тянул бы 1.8 ГБ); `have_nim()` больше ничего не пишет в
stdout; после успешного `koch boot` из дерева удаляются `csources_v2`,
`nimcache` и `.git`. Установка весит **65 МБ** вместо 2.0 ГБ.

**Как нашли.** Прогнав скрипт *до конца* в окружении, где Nim действительно
отсутствовал. Прежняя проверка («четыре режима») убеждалась лишь в том, что
сборка **стартует**, а не в том, что она **завершается** — ровно та ошибка,
из-за которой дефект вообще дожил до продакшена. Теперь скрипт выполняется
целиком на каждом билде CI, так что регрессия станет красной, а не тихой.

**Проверено.** `Nim Compiler Version 2.2.4`; повторный запуск — 9 мс и одна
строка в stdout; все шесть режимов (Nim на PATH / `NIM=` годный / `NIM=` мусор /
`NIM=` слишком старый / `NIM=` несуществующий / Nim есть только в каталоге
сборки) дают ровно одну строку при успехе и ноль строк плюс внятный stderr при
отказе.

## Что делает CI

`.github/workflows/ci.yml`, три задачи. Ни одна не предполагает, что Nim или
браузер кто-то поставил руками.

| Задача | Что делает |
|---|---|
| `suite` | собирает Nim 2.2.4 из исходников через `bootstrap_nim.sh` (это и есть проверка D12/N8), ставит `jsdom` через `npm ci`, прогоняет `tester.nim` целиком |
| `fuzz` | та же обезьяна на трёх других seed'ах и по 300 шагов на приложение: фикс, который выживает только на seed 20261019, не проходит |
| `portability` | `macos-latest` и `windows-latest`: нативные драйверы (Cocoa / WinAPI), которые на Linux не компилируются вовсе, плюс все веб-тесты |

Два жёстких гейта поверх «тесты зелёные»:

- **Браузерные стадии обязаны выполниться.** `ubuntu-latest` поставляется с
  Chrome, поэтому строка `no browser installed` в логе означает не «нет
  браузера», а «тест перестал его находить» — а это молча превратило бы 18
  настоящих проверок в 18 заглушек. Именно так они и выглядели всё это время.
- **`exported_html/` обязан совпадать с закоммиченным.** Бандл
  перегенерируется и сравнивается с HEAD; расхождение — красный билд. Репо уже
  совершало эту ошибку (пример изменили, бандл нет). Экспорт детерминирован:
  повторная генерация даёт побайтово тот же файл, что и в коммите.

## Что именно измеряет обезьяний тест

**D3 проверяется по идентичности, а не по содержимому.** `viewport.innerHTML =
frame` может дать побайтово ту же разметку — и всё равно уничтожить фокус,
выделение и прокрутку, потому что узлов, которые их держали, больше нет.
Поэтому проба отвечает на вопрос «те ли это объекты», а не «тот ли это текст»:

* на viewport навешивается перехват сеттера `innerHTML` — любое присваивание
  считается;
* `MutationObserver` считает структурные изменения; замер, где их не было
  вовсе («тихий кадр»), обязан сохранить **каждый** элемент тем же объектом;
* опубликованное число узлов сверяется с фактическим (см. N6);
* структурная работа сравнивается со стоимостью полной перезаписи — столько же
  кадров, по цене «всё удалить и вставить заново».

Порог 0.75 выбран по мутационному тесту: настоящая реализация даёт 0.41–0.57,
откат к `innerHTML` — 0.81.

**Проверка «ничего за холстом» сознательно сужена до подписей и картинок.**
Прямоугольники, точки и линии исключены: у рисующего приложения это
*содержимое*, а не оформление. `paint` хранит каждый штрих в абсолютных
координатах, полученных из перетаскивания, и при сжатии окна старые штрихи
законно оказываются снаружи нового холста. Подпись или картинка за краем —
всегда ошибка раскладки, потому что так приложение подписывает само себя.

Текст внутри `.uir-clip` тоже исключён: контейнер клипа затем и существует,
чтобы прятать прокрученное за границу панели.

**Обезьяна не нажимает Escape.** Это клавиша завершения у `hello`, `paint` и
`web_showcase`: убив приложение на середине прогона, тест дальше измеряет
замёрзший DOM — не бекенд, а труп. Завершение по Escape проверяется в
`tests/server_monkey_test.nim`, где оно и есть предмет теста.

**jsdom не выполняет настоящую CSS-раскладку** — боксы он синтезирует. Для
проверок выше это не мешает: они смотрят на атрибуты `style`, которые драйвер
пишет сам, и на идентичность узлов, а не на результаты layout. А вот
`getBoundingClientRect` как источник истины о *визуальной* геометрии под jsdom
не годится — для этого нужен настоящий браузер
(`tests/monkey_browser_test.nim`, `UIRELAYS_BROWSER=…`).
